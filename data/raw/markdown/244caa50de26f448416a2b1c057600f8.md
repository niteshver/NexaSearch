# Hybrid Analysis for Secure MCP Tool Use in LLM Agents
Ping He  Zhejiang University Yuexiang Xie  Yaliang Li  and  Shouling Ji  Zhejiang University
###### Abstract.
The rapid development of large language model (LLM) agents has enabled their broad adoption across diverse real-world tasks. To standardize interactions between LLM agents and external environments, Model Context Protocol (MCP) tools have emerged as a de facto standard and have been widely integrated into these systems. However, the use of MCP tools also introduces new safety risks, as LLM agents can be induced to perform malicious or unauthorized actions. Although prior work has proposed defenses for securing tool use in LLM agents, most methods rely on static analysis, i.e., inspecting prompts and generated outputs, which limits the defense effectiveness and robustness. To address these limitations, we propose MTGuard, a hybrid analysis-based defense framework designed to safeguard the use of MCP tools in LLM agents by leveraging lifecycle-aware static-dynamic co-analysis. Extensive evaluation demonstrates that MTGuard effectively mitigates multiple categories of harmful tool use across different LLM agents while maintaining performance on benign user tasks.

##  1. Introduction
Recent advances in large language models (LLMs) have led to the rapid development of LLM agents that can solve complex real-world tasks by planning, invoking tools, and interacting with external environments (Zhang et al., 2024; Yu et al., 2024; Li et al., 2025b; Yang et al., 2024; Li et al., 2025c; Chang et al., 2026; Mok et al., 2025; OpenClaw, 2026). To support standardized interaction between agents and external resources, the Model Context Protocol (MCP) (Anthropic, 2026) has emerged as a de facto standard for tool integration. However, the same unified interface also introduces a critical security boundary: an untrusted or compromised MCP tool can influence an agent’s decisions and cause harmful side effects in the host environment. For example, tool poisoning attacks (Labs, 2026b; He et al., 2025b) can manipulate an agent into invoking tools with unsafe arguments or performing unintended actions. Securing the entire MCP tool invocation lifecycle is therefore essential for deploying LLM agents in real-world applications.
Existing defenses (Xiang et al., 2025; Jing et al., 2025; Tencent Zhuque Lab, 2025; Labs, 2026a; Sha et al., 2025; Deng et al., 2026; Li et al., 2026b; Chen et al., 2025) for LLM tool use operate primarily on information available at the message level, such as user prompts, conversation histories, tool metadata, tool descriptions, invocation parameters, and textual results. Although these approaches can identify suspicious instructions or inconsistencies in tool metadata, they generally do not observe the system-level side effects produced during tool execution. This design leaves a fundamental blind spot: a malicious MCP tool can appear benign in its metadata and returned messages while performing harmful actions at runtime, such as accessing sensitive files, spawning unexpected subprocesses, or communicating with untrusted endpoints.
However, closing this blind spot requires more than directly applying conventional sandboxing or runtime monitoring. Although sandboxing and runtime monitoring are mature techniques in traditional software security, MCP tool usage protection introduces a distinct semantic gap. Low-level execution traces alone do not directly reveal whether a behavior is unsafe; the same file access or network request may be benign or suspicious depending on the tool’s declared functionality, input parameters, and the agent’s task context. An effective MCP defense must therefore connect runtime side effects with the semantic context of the invocation. This observation motivates a hybrid approach that combines contextual inspection of MCP messages with dynamic analysis of tool execution.
To bridge this gap, we propose a hybrid analysis-based defense framework that serves as an MCP tool usage guard for LLM agents, termed MTGuard. At a high level, MTGuard is deployed as a separate guard agent that protects the target LLM agent throughout the MCP tool invocation process. Instead of treating a tool invocation as a static message or treating runtime monitoring as a standalone sandboxing mechanism, MTGuard couples both views throughout the tool use lifecycle. The static view provides the semantic context needed to understand what the tool is supposed to do, whereas the dynamic view provides execution evidence about what the tool actually does. This combination enables MTGuard to detect attacks that are invisible to either view alone, especially tool execution hijacking, where the tool call appears benign, but the executed behavior is malicious.
In practice, MTGuard examines tool calling parameters before execution, monitors tool behavior during execution, and audits execution results after completion, consisting of three components: the pre-execution parameter auditor, the in-execution behavioral monitor, and the post-execution result verifier. This design follows the natural lifecycle of MCP tool invocation, which can be divided into three stages: pre-execution, in-execution, and post-execution. Correspondingly, the pre-execution auditor and post-execution verifier apply user-defined textual and code safety policies to inspect tool parameters and execution results, respectively. Depending on the stage at which a violation is detected, MTGuard rejects the invocation, terminates the running tool, or withholds the unsafe result and returns a denial message to the target agent.
For runtime analysis, the behavioral monitor executes each MCP tool within a controlled sandbox and records its system-level behaviors during execution. To make runtime traces actionable for MCP tool usage safety analysis, the behavioral monitor introduces a novel data structure, termed the tool behavior tree. Unlike a conventional process tree, which primarily represents parent and child relationships among processes, the tool behavior tree is rooted at an MCP tool invocation and organizes heterogeneous runtime events, including process activities, file operations, and network communications, according to their provenance and execution dependencies. This representation transforms fragmented low-level audit logs into an interpretable description of tool behavior. By analyzing the tree together with the tool description, invocation parameters, safety policies, and agent task context, MTGuard can determine whether the tool’s observed behavior is consistent with its declared and intended functionality. The resulting semantic connection between protocol-level context and execution-level evidence enables MTGuard to detect attacks that are difficult to identify from either source alone.
We evaluate MTGuard in two representative safety-critical LLM agent scenarios derived from the MCP-SafetyBench , namely browser automation agent (Ning et al., 2025; He et al., 2024; Chae et al., 2025) and financial analysis agent (Zhang et al., 2024; Yu et al., 2024; Li et al., 2025a, 2026a), using multiple backend LLMs under three MCP attack settings. This setup enables us to examine the effectiveness and efficiency of MTGuard across diverse tasks and adversarial conditions. Experimental results show that MTGuard consistently improves the security of MCP tool use in real-world LLM agent applications. Compared with existing baselines , MTGuard achieves stronger defense performance while incurring low runtime overhead. Across the evaluated settings, MTGuard detects an average of 48.3% of unsafe MCP tool calls, compared with 8.3% for the evaluated baseline methods. In the meantime, MTGuard maintains an average false positive rate of 3.7%, indicating limited disruption to benign tool use and the normal functionality of the target LLM agents. In addition, MTGuard introduces only a modest runtime overhead, with an average additional latency of about 10 seconds in total across the evaluated settings. Our ablation study further demonstrates the importance of combining multiple analysis stages: the pre-execution-only variant cannot detect attacks whose malicious behavior emerges only during host-side execution, whereas the complete MTGuard consistently provides the strongest protection.
The key contributions of this paper are summarized as follows:
  * •
We identify a runtime observability blind spot in existing MCP tool-use defenses and propose MTGuard, a hybrid defense framework that combines protocol-level contextual inspection with dynamic execution analysis.
  * •
We design a lifecycle-aware protection architecture consisting of a pre-execution parameter auditor, an in-execution behavioral monitor, and a post-execution result verifier. We further introduce the _tool behavior tree_ , which organizes heterogeneous system events and their execution dependencies into an interpretable representation of MCP tool behavior.
  * •
We conduct extensive experiments in browser automation and financial analysis scenarios across multiple backend LLMs and MCP attack settings. The results show that MTGuard substantially improves the detection of unsafe tool calls while maintaining a low false-positive rate and moderate runtime overhead.

##  2. Background
###  2.1. LLM agents
LLM agents extend LLMs with the ability to reason, plan, and act in external environments. A common design follows the reasoning-and-acting paradigm (Gan et al., 2024; Yao et al., 2023; Shinn et al., 2023), in which an agent iteratively interprets the user request and current observations, selects an external tool, constructs its invocation parameters, and incorporates the returned result into subsequent reasoning. This paradigm has enabled a wide range of applications, including financial analysis (Zhang et al., 2024; Yu et al., 2024), scientific research (Huang et al., 2025; Baek et al., 2025), and web automation (He et al., 2024; Li et al., 2025d). External tool use is therefore a fundamental capability of modern LLM agents.
To standardize communication between LLM agents and external tools, Anthropic introduced the Model Context Protocol (MCP), an open protocol that provides a unified interface for connecting AI applications to external data sources and services (Anthropic, 2026). In a typical MCP deployment, an MCP host operates the LLM agent, an MCP client manages communication with one or more MCP servers, and each server exposes a collection of tools described by their names, descriptions, and input schemas. When the agent selects a tool, the client sends an invocation request to the corresponding server, which executes the tool implementation and returns the result. An MCP tool may invoke remote APIs, access local resources, or execute code to perform the requested action. Moreover, third-party MCP servers may be distributed and deployed locally. In such deployments, their tool implementations can interact with host resources under the permissions available to the server process, making their actual runtime behavior security-relevant.
For security analysis, we partition the MCP tool invocation lifecycle into three stages. In the _pre-execution stage_ , the agent selects an MCP tool and constructs its invocation parameters based on the user request, task context, and tool metadata. In the _in-execution stage_ , the MCP server executes the tool implementation, which may interact with local host resources or remote services to perform the requested action. In the _post-execution stage_ , the tool result is returned to the MCP host and incorporated into the agent’s context for subsequent reasoning and decision-making.

Threat model. Following the taxonomy of MCP-SafetyBench , we consider attacks originating from three representative attack surfaces: the MCP server, the MCP host, and the user. These attack-source categories cover the major interfaces of MCP-enabled LLM agents through which adversarial influence can alter agent decisions or tool execution. In MCP server-side attacks, the adversary controls or compromises server-provided components, such as tool metadata, tool descriptions, returned payloads, or tool implementations. Such control may manipulate tool selection or invocation parameters, inject malicious instructions into tool results, or cause tools to perform unauthorized operations. In MCP host-side attacks, the adversary tampers with the host’s planning, orchestration, or message-routing logic. Such manipulation may alter the agent’s intended task, replace or redirect a selected tool invocation, modify intermediate messages or tool results, forge identity information, or replay previously valid interactions. In user-side attacks, the adversary controls the user request or user-provided resources, such as prompts, files, or external content. Adversarial inputs may induce the agent to misuse otherwise legitimate MCP tools, potentially resulting in malicious code execution, credential disclosure, persistent unauthorized access, retrieval-agent deception, or excessive-privilege misuse.
The adversary’s goal is to induce unsafe tool usage that either disrupts the intended task or produces unauthorized effects in the host or external environment. We assume that only one of the above attack surfaces is compromised in each attack instance and that the adversary cannot directly compromise the defense system or its trusted monitoring infrastructure. The defender aims to detect and deny unsafe tool usage while preserving benign and task-relevant invocations. We exclude training-time attacks against the underlying LLM, model-weight tampering, compromise of the defense system itself, kernel-level compromise, attacks outside the MCP tool invocation lifecycle, and attacks that simultaneously compromise multiple attack surfaces. Colluding attacks that simultaneously compromise multiple attack surfaces are also outside the scope of this work.
##  3. Methodology
###  3.1. Design overview
At a high level, MTGuard is a hybrid analysis-based defense framework that safeguards MCP tool usage by LLM agents through the joint analysis of static context and dynamic execution behavior. In deployment, MTGuard operates as an external guard agent that intercepts the MCP tool invocation pipeline of a target LLM agent. As illustrated in Figure , the framework consists of three components: a pre-execution parameter auditor, an in-execution behavioral monitor, and a post-execution result verifier. The detailed algorithmic description of MTGuard can be found in Appendix .
###  3.2. Pre-execution parameter auditor
The pre-execution parameter auditor identifies unsafe or policy-violating MCP tool invocations before they are dispatched to the tool executor. For each intercepted invocation, the auditor collects the pre-execution context available at the target agent’s tool-call boundary. This context includes the target agent’s conversation history, the current user task, the declared tool name, the invocation parameters, and the registered parameter schema of the selected tool. The auditor retrieves the conversation history from the target agent’s memory and treats the most recent user message as the current task. It obtains the tool schema from the registry exposed by the target agent, ensuring that the guard analyzes the same schema used for the agent’s tool selection. Because free-form tool descriptions may contain adversarial instructions, the auditor removes them and retains only the tool name and parameter specification.
The auditor evaluates two categories of user-defined safety policies: programmatic policies and natural-language policies. Programmatic or code-level policies are trusted executable functions that operate on the structured pre-execution context and return a binary decision together with a justification. The auditor evaluates these policies first and immediately rejects the invocation if any applicable programmatic policy is violated. If the programmatic policies are satisfied, the auditor evaluates the natural-language or text-level policies using an LLM. A fixed system prompt specifies the auditor’s general security principles, while the user prompt instantiates the current user task, conversation history, tool name, parameter schema, invocation arguments, and applicable policy rules. The tool’s free-form description is intentionally excluded from this prompt to prevent poisoned metadata from directly influencing the guard model. The full system prompt (Prompt ) and user prompt template (Prompt ) are provided in Appendix . If either policy path returns a denial, MTGuard rejects the invocation before it is dispatched and returns a denial response to the target LLM agent. Otherwise, MTGuard starts behavioral monitoring and allows the invocation to proceed to the tool executor.
###  3.3. In-execution behavioral monitor
The in-execution behavioral monitor collects system-level evidence about the runtime behavior of an MCP tool executed inside a controlled sandbox. Before the target invocation is forwarded to the tool executor, MTGuard starts the monitor; after the tool returns, it stops the monitor and retrieves the collected events. The behavioral monitor is an evidence-collection component and does not itself issue a safety verdict during execution. Instead, its output is organized into a tool behavior tree and subsequently analyzed by the post-execution result verifier.
OS-level event capture. MTGuard uses host-side eBPF instrumentation to observe MCP tools executed inside a Docker-backed sandbox. The monitor identifies the target container using its cgroup v2 identifier and attributes runtime events to the corresponding container cgroup. For each intercepted tool invocation, MTGuard clears previously collected events and starts tracing before forwarding the call to the tool executor. At the beginning of the monitoring interval, it adds all existing processes in the container cgroup to the tracked-process set, because long-lived MCP server workers may have been created before the current invocation. Newly forked processes are subsequently added to the tracked set, enabling the monitor to capture both pre-existing server processes and their descendants. Tracing stops after the tool returns and the event stream becomes idle.
The monitor collects process, file, network, and DNS-response events. Process events include process creation, execution, execveat, and termination, together with process identifiers, executable names, and command-line arguments. File events include file opening, deletion, and renaming and are associated with the responsible process; the current implementation records file names rather than reconstructed absolute paths. Network events capture TCP connection, acceptance, listening, and connection-establishment activities, together with IP addresses, ports, and process identifiers. The monitor also records the occurrence of UDP DNS responses from port 53 within the target cgroup. Because these DNS-related events may not be attributable to a node in the captured process hierarchy, they are retained separately and associated with the invocation through the container cgroup and monitoring interval.
Tool behavior tree. Based on the collected execution events, the monitor constructs a tool behavior tree associated with the intercepted MCP tool invocation. Conceptually, the tree is rooted at the declared invocation and records its call identifier, tool name, and invocation parameters. The root contains two logical branches: a process branch and a DNS branch.
The process branch contains one or more process trees constructed from the processes observed in the sandbox cgroup during the invocation. Each process node records the host and container process identifiers, parent-process identifiers, executable name, command-line arguments, and process lifetime events. File and network events are attached to the process node responsible for generating them. Parent and child edges represent the observed process-creation relationships, allowing descendant processes spawned during tool execution to be connected to their originating processes. The DNS branch stores DNS-response events attributed to the same sandbox cgroup and monitoring interval but not reliably attached to a process node in the process branch. By associating the declared tool invocation with its process hierarchy, file operations, network activities, and DNS-related behavior, the tool behavior tree provides a unified representation of the tool’s observed execution. The behavioral monitor returns the raw behavior tree together with the tool execution result for post-execution verification.
###  3.4. Post-execution result verifier
The post-execution result verifier determines whether the observed runtime behavior and returned result of an MCP tool are consistent with the user task, declared invocation, and applicable safety policies. Unlike the pre-execution auditor, which operates only on information available before dispatch, the verifier additionally uses the execution result and the system-level evidence collected by the behavioral monitor. It compares the tool name, parameter schema, and declared invocation arguments with the observed process activities, file operations, network events, DNS-response events, and returned content. This declared-versus-observed comparison enables the verifier to detect unsafe behavior, including host-side tool-invocation hijacking, that is not visible from the declared invocation alone.
Before LLM-based verification, MTGuard simplifies the raw tool behavior tree to reduce infrastructure noise and control the prompt length. The simplification preserves process identities, executed commands, and file and network events not matched by the configured noise rules. The filtered events primarily include Python bytecode and import artifacts, accesses to commonly loaded shared libraries, and loopback network communication treated as sandbox-internal traffic. The raw behavior tree is retained for programmatic policy evaluation, while the simplified representation is supplied to the LLM-based verifier. To bound the LLM input size, MTGuard truncates overly long serialized process and DNS-event records and limits the amount of tool-result content included in the audit prompt. An example of the simplified tool behavior tree is provided in Appendix .
The post-execution result verifier evaluates two categories of user-defined safety policies: programmatic policies and natural-language policies. Programmatic or code-level policies operate directly on the static invocation context, raw tool behavior tree, DNS-response events, and tool execution result. Each policy returns a binary decision together with a justification. These policies are evaluated first, and a denial immediately terminates post-execution verification. If the programmatic policies are satisfied, the verifier evaluates the natural-language, or text-level, policies using an LLM. The verifier uses a fixed system prompt to define its decision principles, while the user prompt instantiates the current user task, conversation history, tool name, parameter schema, declared invocation arguments, execution result, simplified process tree, DNS-response events, and applicable policy rules. The prompt structures verification as a declared-versus-observed consistency check, requiring the model to compare the declared invocation with the actual execution evidence. The LLM-based verifier follows an allow-by-default decision rule and returns a denial only when the available evidence demonstrates a clear mismatch or an explicit policy violation. To improve verification reliability, the prompt provides a step-by-step analysis procedure and few-shot examples covering both benign executions and representative security violations. The full system prompt (Prompt ) and user prompt template (Prompt ) are provided in Appendix . If either policy path returns a denial, MTGuard classifies the completed execution as unsafe, withholds the tool result, and returns a denial response to the target LLM agent. Otherwise, the verified result is forwarded to the agent. Because this decision is made after execution, post-execution denial prevents the result from influencing subsequent agent reasoning but does not by itself roll back side effects that have already completed.
##  4. Experiments
###  4.1. Experimental setup
Implementation details. MTGuard is a hybrid analysis-based defense framework consisting of three components for securing MCP tool usage. We implement a prototype of MTGuard primarily in Python, with the eBPF tracing programs implemented in C. Specifically, we build the main pipeline on top of AgentScope . For controlled MCP tool execution, we use Docker as an isolated sandbox environment, and we employ eBPF to capture the runtime behavior of each tool. For text-level policy auditing, MTGuard consistently uses DeepSeek-V4-Pro as the backend LLM across all experimental settings.
LLM agents and benchmark tasks. We derive our evaluation from two representative domains in MCP-SafetyBench : browser automation and financial analysis. For each domain, we implement a ReAct-style LLM agent using the MCP servers and task configurations provided by the benchmark. The browser automation agent primarily interacts with a Playwright MCP server to perform tasks involving flight booking, map search, Hugging Face, academic-paper search, and sports websites. The financial analysis agent primarily interacts with a Yahoo Finance MCP server to retrieve and analyze financial data. Both agents can additionally access auxiliary MCP servers, including filesystem, terminal, and network-fetching tools. We limit each agent run to at most 20 reasoning-and-acting iterations.
From MCP-SafetyBench, we select 30 browser automation cases and 53 financial analysis cases, resulting in 83 original attack-instrumented cases. Each case contains a user objective, an expected output schema, an attack configuration, and an execution-based evaluator for determining whether the attack succeeds. We further introduce 16 MCP host-side Tool Call Hook cases, with 8 cases for each domain, resulting in 38 browser-automation cases and 61 financial-analysis cases. Thus, the final evaluation suite contains 99 attack-instrumented cases. We instantiate both agents with three backend LLMs using the model identifiers DeepSeek-V4-Flash, DeepSeek-V4-Pro, and GPT-5.6 Luna.

Attack methods. Following MCP-SafetyBench, we organize the evaluated attacks according to their attack sources: MCP server-side, MCP host-side, and user-side attacks, as discussed in Section . The selected server-side cases cover tool poisoning, function overlapping, preference manipulation, tool shadowing, function-return injection, and rug-pull attacks. The original host-side cases cover intent injection, data tampering, and replay injection. The user-side cases cover malicious code execution, credential theft, and remote access control. Overall, the selected MCP-SafetyBench cases contain 62 server-side cases, 10 host-side cases, and 11 user-side cases.
In addition to the original benchmark attacks, we introduce a new MCP host-side attack termed _Tool Call Hook_. This attack models a compromised host dispatch layer that hijacks an agent-generated tool invocation immediately before it reaches the tool executor. Specifically, the hook replaces a designated benign tool invocation with terminal::run_command and supplies an unauthorized shell command. For example, a browser call to playwright_navigate or a financial-data call to get_historical_stock_prices may be replaced with cat /etc/passwd. The 8 payloads in each domain cover unauthorized accesses to system and user-configuration files, security-sensitive file probes, and persistence-related modifications. Each hook is triggered at most once in a task. The hook is inserted after the agent has generated the declared tool call and after the pre-execution auditor has inspected that declaration, but before the actual tool executor is invoked. Therefore, the pre-execution auditor observes the benign agent-declared call, whereas the behavioral monitor records the runtime behavior of the substituted terminal command. This setting directly evaluates whether runtime behavior analysis can detect execution-layer hijacking that is invisible from the declared tool call alone.
After adding eight Tool Call Hook cases to each domain, the browser-automation setting contains 22 server-side, 11 host-side, and 5 user-side cases, while the financial-analysis setting contains 40 server-side, 15 host-side, and 6 user-side cases. The complete evaluation suite therefore contains 62 server-side, 26 host-side, and 11 user-side cases, for a total of 99 cases spanning 18 fine-grained attack categories.
Baseline methods. We compare MTGuard with two runtime defense components provided by Agent-Aegis : Tool Call Governance (TCG) and Tool Result Inspection (TRI). Because the released Agent-Aegis implementation is written in TypeScript, we implement MCP-compatible Python adaptations of the two components in our evaluation framework.
TCG operates before tool execution and inspects the agent-declared tool name and arguments. Our implementation ports Agent-Aegis’s rules for high-risk shell commands and command obfuscation and adapts them with MCP-SafetyBench-specific checks for protected paths and dangerous shell behaviors. TRI operates after tool execution and treats the returned tool content as untrusted input. It scans the textual result for patterns related to role takeover, policy bypass, tool induction, secret requests, and data exfiltration. Our TRI adaptation performs detection only and does not sanitize or rewrite tool results. For a fair comparison, both baselines are replayed over the same tool-call records collected from the executions of MTGuard.
Metrics. We evaluate the defenses at the tool-call level using detection rate (DR), false positive rate (FPR), and auditing latency. Individual tool calls are labeled using the attack-specific evaluator associated with each benchmark case. A call is labeled unsafe if its observed invocation or returned result satisfies the corresponding attack-success signature; all other labeled calls are treated as safe. ###  4.2. Defense effectiveness
We first evaluate the attacks against the target LLM agents without defense to verify that they can induce unsafe MCP tool invocations. The attack success rates are reported in Appendix . We then evaluate MTGuard under the same attack settings. To enable a consistent tool-call-level comparison, the pre-execution auditor, behavioral monitor, and post-execution verifier are invoked at their original positions in the online tool-use pipeline, but their denial decisions do not block tool execution or modify tool results. Instead, each decision is recorded as a counterfactual enforcement verdict indicating whether the corresponding call would be denied in deployment. This protocol preserves the complete agent trajectory, allows post-execution behaviors to be collected even when the pre-execution auditor raises an alert, and enables all defenses to be evaluated over the same tool-call traces. For DR, we include only tool calls whose unsafe behavior is confirmed by the attack-specific evaluator.
For the policy configuration, we enable seven deterministic function rules in the pre-execution parameter auditor. These rules detect sensitive-file access, dangerous shell commands, SSH persistence, off-task suspicious URLs, shadowed tool names, task and ticker mismatches, and repeated navigation to the same URL, with the repetition threshold set to three. The function rules are evaluated before LLM-based auditing and immediately produce a denial verdict when a violation is found. We additionally configure three natural-language policy rules for both the pre- and post-execution LLM auditors. These rules prohibit task-irrelevant access to credentials, shell initialization files, SSH keys, and privilege probes; reject navigation or fetching of suspicious off-task endpoints; and require tool arguments such as tickers, destinations, and websites to remain consistent with the user task rather than poisoned tool metadata. The pre-execution auditor evaluates these policies using the task context, tool name, parameter schema, and declared arguments. The post-execution verifier additionally receives the execution result, tool behavior tree, and DNS events, allowing it to compare the agent-declared invocation with the behavior that was actually executed. This configuration combines low-cost deterministic detection of known attack signatures with LLM-based semantic analysis of task alignment and declared-versus-actual behavioral consistency.

Across the six agent and model configurations, MTGuard detects 116 of 240 unsafe tool calls, achieving an overall DR of 48.3%. In comparison, TCG detects 20 unsafe calls and achieves a DR of 8.3%, while TRI does not detect any unsafe calls in the evaluated traces. The advantage of MTGuard is particularly evident for MCP host-side attacks: it detects 48 of 64 unsafe calls, corresponding to a DR of 75.0%, whereas both baselines achieve 0.0%. Defense effectiveness also differs substantially across attack sources. MTGuard achieves a DR of 100.0% (16/16) against user-side attacks because these attacks produce explicit malicious commands or sensitive-resource accesses that can be recognized from the declared arguments. For host-side attacks, MTGuard achieves 75.0% (48/64), with its detections concentrated on the Tool Call Hook attacks that produce an explicit declared-versus-actual inconsistency. The DR is lower for server-side attacks, at 32.5% (52/160). Many server-side attacks manipulate tool selection, parameters, preferences, or returned values while continuing to invoke legitimate tools through syntactically valid arguments. Consequently, their execution traces may remain close to normal tool behavior, making them more difficult to identify than explicit command execution or tool-call hijacking.
From the agent-domain perspective, MTGuard achieves an aggregate DR of 52.6% (51/97) for the browser automation agent and 45.5% (65/143) for the financial analysis agent. The higher overall DR in browser automation is partly explained by server-side attacks involving suspicious URLs, shadowed navigation tools, and repeated navigation patterns, which provide observable signals in tool names, arguments, or network behavior. In contrast, many attacks in financial analysis alter tickers, preferences, or returned financial values while preserving the expected structure of legitimate Yahoo Finance calls. Such semantic manipulations may produce plausible arguments and normal-looking runtime traces, making them harder to distinguish from benign financial operations.
FPR. We further evaluate whether the defenses incorrectly flag safe MCP tool calls. As shown in Table , MTGuard maintains a relatively low FPR across the evaluated configurations. Its unweighted average FPR across the six agent and model configurations is 3.7%, compared with 0.3% for TCG and 0.4% for TRI. Although MTGuard has a higher FPR than the rule-based baselines, it provides substantially broader detection coverage, particularly for server-side and host-side attacks. The FPR of MTGuard is slightly higher for browser automation, averaging 3.9%, than for financial analysis, which averages 3.4%. Browser tasks involve longer and more heterogeneous interaction trajectories, including repeated navigation and transitions across external websites. Some of these benign behaviors may resemble replay or off-task navigation and consequently trigger the corresponding deterministic or semantic checks.
The low overall FPR is supported by the conservative decision principles used in the LLM-based auditors. In particular, the post-execution verifier adopts an allow-by-default policy for behavior that is consistent with the declared invocation and requires clear evidence of hijacking, task-irrelevant sensitive access, or suspicious network activity before returning a denial. The structured prompts further require the auditor to examine task alignment, argument integrity, policy compliance, and declared-versus-actual consistency before making its decision.

As shown in Figure , the average pre-execution audit latency is 5.93 seconds for browser automation and 5.68 seconds for financial analysis. The corresponding post-execution audit latency is 6.74 and 6.40 seconds, respectively. Thus, when both LLM auditing stages are invoked, they introduce approximately 12.39 seconds of additional latency per tool call.
These measurements include only LLM-based audit latency and exclude the near-zero-cost deterministic function-rule checks, tool execution time, and sandbox or eBPF monitoring costs. ###  4.3. Ablation study
To evaluate the contributions of the two analysis stages, we construct a PRA-only variant that retains only the pre-execution parameter auditor and a PRV-only variant that retains the behavioral monitor and post-execution result verifier. As shown in Table , PRA and PRV achieve overall DRs of 25.0% and 31.7%, respectively, both substantially lower than the 48.3% achieved by the full MTGuard. Moreover, the full system consistently outperforms both variants across all six agent and model configurations.
The two stages exhibit complementary strengths across attack sources. PRA detects all user-side unsafe calls because their malicious commands or sensitive paths are visible in the declared tool arguments, but it fails completely on host-side attacks, where the invocation is hijacked only after pre-execution inspection. Conversely, PRV detects 75.0% of host-side unsafe calls by comparing declared invocations with observed runtime behavior, but detects only 6.3% of user-side calls. For server-side attacks, the full system achieves 32.5%, outperforming both PRA at 27.5% and PRV at 16.9%. These results demonstrate that pre-execution inspection and runtime-aware post-execution verification address different failure modes; using either stage alone is suboptimal, while their combination provides broader protection.
##  5. Discussion
###  5.1. Limitations & Future work
Generality. MTGuard uses MCP as its reference interface because MCP standardizes tool schemas, invocation arguments, and response messages. Conceptually, the framework may be adapted to other tool-use interfaces, including function-calling APIs, LangChain tools, local functions, shell commands, and REST API wrappers. Such an adaptation would map tool metadata, arguments, execution boundaries, and returned values to the corresponding inputs of MTGuard. However, this extension requires a well-defined interception boundary and sufficient control over the tool execution environment. Tools executed remotely or on platforms without compatible sandboxing and system-level tracing may require additional provider-side instrumentation. Therefore, although the design is not inherently restricted to MCP, our current prototype and evaluation focus exclusively on locally deployed MCP tools.
Runtime visibility and containment. The detection capability of MTGuard is bounded by the runtime signals visible to its behavioral monitor. Currently, MTGuard captures process, file, and network events, including DNS-related metadata, but does not inspect network payloads or application-level data flows. It may therefore miss malicious behavior hidden in encrypted traffic, in-memory computation, or unobserved external services. Moreover, post-execution verification detects unsafe behavior only after the tool has executed. Although MTGuard can suppress an unsafe result, it cannot automatically undo system-level side effects that have already occurred. Future work could incorporate richer data-flow signals, payload-aware network inspection, selective online termination, and transactional execution or rollback mechanisms.
###  5.2. Potential ethical concerns
The goal of this study is to improve the security of MCP tool usage in LLM agents. Our evaluation uses benchmark-derived attacks and additional host-side tool-call hijacking cases that execute potentially harmful system commands. Although these payloads have dual-use potential, they consist of well-known security-testing operations and are used solely to evaluate defensive mechanisms. All malicious commands are executed inside disposable Docker sandboxes without real user data or credentials, and we do not target third-party or production agent systems. We disclose representative examples only to support reproducibility, and any released artifact will clearly identify dual-use content and provide safe reproduction instructions for isolated environments, following established practices in prior security research .
##  6. Related work
Guardrails have emerged as an important defense mechanism for improving the safety of LLMs and LLM agents (Xiang et al., 2025; Rebedea et al., 2023; Yuan et al., 2024; Inan et al., 2023; Liu et al., 2025; Deng et al., 2026; Liu et al., 2026; Luo et al., 2025; Chennabasappa et al., 2025). Most existing guardrail methods focus on content-level protection, such as filtering harmful or violent outputs. However, such content-level guardrails are insufficient for LLM agents, whose safety requirements are more diverse and often depend on tool usage and execution context. To address this limitation, recent studies (Xiang et al., 2025; Liu et al., 2025) have proposed guardrail mechanisms specifically for LLM agents. For example, Xiang et al. propose GuardAgent, which enforces access control over target LLM agents. Liu et al. detect abnormal agent behaviors through anomaly detection over behavioral messages. However, these methods rely primarily on static messages or interaction traces to identify unsafe tool usage. As a result, they cannot effectively detect tool execution hijacking attacks because they do not incorporate the dynamic behaviors revealed during tool execution.
In parallel, recent works (Jing et al., 2025; Tencent Zhuque Lab, 2025; Labs, 2026a) have studied the detection of malicious MCP tools by analyzing MCP server packages. For instance, A.I.G (Tencent Zhuque Lab, 2025) employs an LLM-based agent to inspect MCP server packages and identify malicious MCP tools. However, these approaches are limited to package-level analysis and do not support runtime monitoring during agent execution. Without runtime information, they cannot provide fine-grained protection over actual tool invocations and therefore achieve limited defense effectiveness.
##  7. Conclusion
This paper presents MTGuard, a hybrid-analysis-based framework for safeguarding MCP tool usage in LLM agents. By integrating pre-execution parameter auditing, runtime behavioral monitoring, post-execution result verification, and the tool behavior tree, MTGuard jointly analyzes static invocation context and dynamic execution behavior. Experiments across two safety-critical agent domains under server-side, host-side, and user-side attacks show that MTGuard substantially outperforms existing baselines while maintaining a low false positive rate and moderate auditing latency, demonstrating its potential for securing real-world LLM agent tool use.

Algorithm summarizes the workflow of MTGuard. For each intercepted invocation, MTGuard first retrieves the target agent’s conversation history and treats the most recent user message as the current user task. It then extracts the declared tool name and invocation parameters together with the corresponding schema registered by the target agent. Because free-form tool descriptions may themselves contain poisoned instructions, MTGuard removes them from the schema supplied to the guard and retains only the tool name and parameter specification. The pre-execution parameter auditor first evaluates the invocation using programmatic or code-level policies. If all applicable programmatic policies are satisfied, it subsequently evaluates the natural-language or text-level policies using the audit LLM. A denial from either policy path causes MTGuard to reject the invocation before it is dispatched. If the invocation passes the pre-execution audit, MTGuard starts the behavioral monitor and forwards the invocation to the target agent’s tool executor. The monitor records the resulting system-level events until the tool execution completes and then organizes them into a tool behavior tree. The raw behavior tree and execution result are supplied to the programmatic post-execution policies, whereas a simplified behavior tree is supplied to the LLM-based verifier. If either post-execution policy path returns a denial, MTGuard withholds the tool result and returns a denial response to the target agent. Otherwise, the verified result is forwarded to the agent.
##  Appendix B Attack effectiveness
To validate the attack settings, we evaluate the server-side, host-side, and user-side attacks against the target LLM agents without defense. We define the attack success rate (ASR) as the fraction of attack-instrumented cases in which the corresponding attack-specific evaluator confirms at least one unsafe MCP tool invocation. Table reports the ASR for each agent and model configuration.
Overall, host-side attacks are the most effective, achieving an aggregate ASR of 87.2% (68/78), compared with 38.2% (71/186) for server-side attacks and 33.3% (11/33) for user-side attacks. The high effectiveness of host-side attacks results from their ability to manipulate orchestration or tool dispatch after the target LLM has generated its intended action, thereby reducing the opportunity for the model to resist the attack. In contrast, server-side attacks must influence the agent through poisoned tool information or results, while user-side attacks rely on the model following an explicitly malicious request. Consequently, their success is more dependent on the target model and task context.
The results also show that GPT-5.6 Luna is relatively resistant to user-side attacks, with ASRs of 20.0% for browser automation and 16.7% for financial analysis. This suggests that it more frequently rejects or avoids translating malicious user instructions into unsafe tool calls. Nevertheless, every evaluated attack source successfully induces unsafe invocations in at least some settings, confirming the need for defenses that cover multiple MCP attack surfaces. In the defense evaluation, DR is computed only over tool calls whose unsafe behavior is confirmed by the attack-specific evaluator; unsuccessful attack cases therefore contribute no unsafe calls to its denominator.
