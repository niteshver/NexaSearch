#   ⟨53⟩ D14 Vision-QA — CAD visual question answering (evaluation benchmark) 
The **Vision-QA layer** of D14 (BenchCAD), packaged separately with its intended usage made explicit: this is an **evaluation benchmark / agentic-setting seed, NOT direct VLM training data.**
**2,400 records** : a 4-view orthographic render of a CAD part + a numeric question + the gold answer. The underlying CadQuery program that generated the part (and the answers) is preserved in `metadata.gt_code`.
##   ⟨49⟩ Why this is not VLM training data 
BenchCAD's Vision QA is one half of a deliberate **matched-pair design** : the _same_ questions are asked given the image (vision QA) and given the CadQuery source (code QA), to _measure_ what vision alone can recover. Most questions ask about the **program structure** ("how many `.workplane()` calls?", "on which line is the first hole operation?") or **exact dimensions** ("largest fillet radius?") — information that is _not present in the pixels_. We verified this empirically with a blind-answerability probe (Claude Sonnet 5, 60 stratified questions, ±5% tolerance):  
| question bucket  | share  | question-only  | + image  | + code  |  
| --- | --- | --- | --- | --- |  
| code-structure (op counts, line numbers…)  | ~48%  | 13%  | 20%  | **60%**  |  
| exact metric (dims, ratios)  | ~23%  | 0%  | **0%**  | **60%**  |  
| numeric-threshold comparisons  | ~17%  | 40%  | 40% _(no lift = prior/guessing)_  | 73%  |  
| genuinely visual (shape family, visible counts)  | ~11%  | 40%  | **66%**  | 80%  |  
Only the _visual_ bucket gains real accuracy from the image. Training a VLM to "reason" its way to the other answers from a render would teach it to fabricate measurements and code facts — so the `reasoning` field is intentionally left `null` here, while the two trainable D14 layers (image→code generation and code editing) are annotated separately.
##   ⟨50⟩ Intended uses 
  1. **Evaluation** : benchmark multimodal CAD understanding; the vision-vs-code accuracy gap per bucket is the interesting measurement (per the matched-pair design).
  2. **Agentic setting** : with tools, all buckets become answerable — e.g. an agent that retrieves the part's program (`metadata.gt_code`) or executes/measures the geometry, then answers. The image+question+gold triples are ready-made tasks for such a loop.
  3. **Open-book QA** : providing `metadata.gt_code` alongside the image turns every record into a well-posed code-comprehension question (BenchCAD's "code QA" modality).


##   ⟨51⟩ Schema   
| field  | content  |  
| --- | --- |  
| `query`  | the question  |  
| `image`  | 4-view orthographic render (PNG)  |  
| `annot`  | `{"answer", "level" (L1–L6), "qa_id", "source", "type" (integer/dim/ratio)}`  |  
| `reasoning`  |  `null` (deliberately — see above)  |  
| `metadata`  | provenance + **`gt_code`**(the CadQuery program; ground truth for all answers)  |  
Scoring convention (from BenchCAD): exact match for integers, ±5% tolerance for dims/ratios. Boolean golds are encoded as integers: yes = 1, no = 0.
